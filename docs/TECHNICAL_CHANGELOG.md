# Technical Changelog

### backend/src/topology/extractor.py

- **2026-07-28:** Initial implementation. Downloads the drivable street network around Malaga's city center via `osmnx.graph_from_point`, using a 2 km bounding box (`dist_type="bbox"`) so that the extracted area is deterministic and easy to reason about. Renders the resulting `MultiDiGraph` with Folium, drawing each edge as a `PolyLine` and each node as a `CircleMarker` on top of an OpenStreetMap-derived tile layer, and saves the result to `backend/data/malaga_preview.html`. At this stage no connectivity filtering or simplification beyond OSMnx defaults (`retain_all=True`) is applied, since the objective was purely to visually validate the raw topology before any routing algorithm is introduced. Note: `osmnx.plot_graph_folium` was not used because it no longer exists in `osmnx==2.1.1`; the Folium rendering is built manually from the graph's edge and node geometries instead.

- **2026-07-28:** Switched the OSMnx `network_type` from `"drive"` to `"drive_service"` in `download_drive_network`. Restricted-access service roads (as commonly found in historical city centers, such as Malaga's) are excluded from the plain `"drive"` filter, yet they are legitimately traversable by delivery vehicles in a VRP context, so omitting them would understate the true routable street network. Added an explicit largest strongly connected component extraction step using `networkx.strongly_connected_components`, since `osmnx` only guarantees weak connectivity by default (a node might be reachable in one direction but not the other once one-way streets are considered). A vehicle routing engine requires that any depot or customer node be mutually reachable from any other node while respecting street directionality, so the graph is now reduced to its largest strongly connected component before being returned. Extended `build_interactive_map` to import `folium.plugins` and attach a `PolyLineTextPath` overlay (repeating "►" glyph) to every edge, so that the direction of travel encoded by each `MultiDiGraph` edge, and therefore the one-way versus two-way nature of each street, is immediately visible on the rendered map rather than being an implicit property of the underlying data.

- **2026-07-28:** Added `compute_edge_travel_times`, which uses `osmnx.add_edge_speeds` followed by `osmnx.add_edge_travel_times` to populate `speed_kph` and `travel_time` attributes on every edge. OpenStreetMap `maxspeed` tags are sparse in practice, so `DEFAULT_HIGHWAY_SPEEDS_KPH` provides sensible per-highway-type free-flow speeds (aligned with typical Spanish urban and interurban limits) to impute missing values, with `FALLBACK_SPEED_KPH` as a last-resort default for any highway type that has neither observed `maxspeed` data nor an entry in that mapping. Edge-weighted travel times are a prerequisite for any shortest-path or dynamic routing computation planned for Phase 2, since the simulation must reason in terms of time, not just distance. Added `save_processed_graph`, which serializes the fully processed `MultiDiGraph` (strongly connected, with speed and travel time attributes) to `backend/data/malaga_graph.pkl` via the standard `pickle` module. Pickle was chosen over text-based formats such as GraphML because `networkx` no longer ships `write_gpickle`/`read_gpickle` (removed in `networkx>=3.0`), and a raw pickle dump preserves the exact in-memory graph object and its attribute types, allowing the backend to deserialize it directly at startup with no parsing overhead, instead of re-downloading and reprocessing the network from OpenStreetMap on every run. The `__main__` block was updated to run the speed/travel-time computation immediately after the strongly connected component filtering and before both the map visualization and the pickle serialization, so the artifact saved to disk is always the final, fully processed graph.
